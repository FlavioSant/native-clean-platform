# Dark mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the boilerplate a working dark theme — every semantic colour alias gets a dark value, the app follows the OS preference with a persisted manual override, and the two raw-colour call sites and the account screen pick it up.

**Architecture:** `tokens.js` gains a `semanticColorsDark` map (same keys, values derived from the existing `brand`/`neutral`/`danger` scales — no new hex). `tailwind.config.js` points every semantic alias at a CSS variable (`var(--color-<key>)`) instead of a literal value. A new `ThemeProvider` (`src/theme/`) applies the active map at runtime via NativeWind's `vars()` on a root `View`, and a `useThemePreference` hook tracks the user's `'system' | 'light' | 'dark'` choice, persisted in `AsyncStorage`, applied through NativeWind's own `colorScheme.set()`.

**Tech Stack:** NativeWind 4.2.6 (`vars()`, `useColorScheme`, `colorScheme` — all already installed), `@react-native-async-storage/async-storage` (new dependency), Expo SDK 57, jest-expo, React Native Testing Library.

**Spec:** [docs/superpowers/specs/2026-09-22-dark-mode-design.md](../specs/2026-09-22-dark-mode-design.md) — read D1–D6 before touching any task; this plan does not repeat the "why," only the "what."

## Global Constraints

- No new brand palette. Every dark value in `semanticColorsDark` comes from `colors.brand`, `colors.neutral` or `colors.danger`, already defined in `src/theme/tokens.js` — never a new hex literal (spec Scope, Out).
- `success`/`warning`/`info` and `danger`'s dark step are **not** extended. `danger-surface` reuses `colors.neutral[800]` in dark (spec D5).
- No `SegmentedControl` primitive in `src/components/` — the account-screen toggle is inline `Pressable`s (spec Scope, Out).
- `@react-native-async-storage/async-storage` is installed via `pnpm exec expo install @react-native-async-storage/async-storage`, never a hand-picked version — this repo pins exact versions, resolved by `expo install` (`ARCHITECTURE.md` §9).
- English only in code and comments, arrow functions everywhere, no magic strings (`AGENTS.md` rules 1, 2, 4) — same as the rest of this codebase; not repeated per task below.
- The exact dark token table (spec D5), needed by Task 1:

  | alias | light (today) | dark (new) |
  |---|---|---|
  | `background` | `neutral[50]` | `neutral[950]` |
  | `surface` | `neutral[0]` | `neutral[900]` |
  | `surface-muted` | `neutral[100]` | `neutral[800]` |
  | `border` | `neutral[200]` | `neutral[700]` |
  | `border-strong` | `neutral[300]` | `neutral[600]` |
  | `content` | `neutral[900]` | `neutral[50]` |
  | `content-muted` | `neutral[500]` | `neutral[400]` |
  | `content-inverse` | `neutral[0]` | `neutral[0]` (unchanged) |
  | `primary` | `brand[500]` | `brand[400]` |
  | `primary-pressed` | `brand[600]` | `brand[500]` |
  | `danger` | `danger[600]` | `danger[500]` |

```ts
// src/theme/useThemeColors.ts
import { useColorScheme } from 'nativewind';

import { semanticColors, semanticColorsDark } from './tokens';

const DARK_SCHEME = 'dark';

/**
 * The semantic colour map for whichever theme is active right now — for the
 * rare call site that needs a literal value instead of a Tailwind class (an
 * `ActivityIndicator`'s `color` prop, for example). Screens use the classes
 * themselves; see `src/theme/README.md`.
 */
export const useThemeColors = (): typeof semanticColors => {
  const { colorScheme } = useColorScheme();

  return colorScheme === DARK_SCHEME ? semanticColorsDark : semanticColors;
};
```

```ts
// src/theme/themePreferenceStorage.ts
import AsyncStorage from '@react-native-async-storage/async-storage';

export const THEME_PREFERENCES = { SYSTEM: 'system', LIGHT: 'light', DARK: 'dark' } as const;
export type ThemePreference = (typeof THEME_PREFERENCES)[keyof typeof THEME_PREFERENCES];

/** Namespaced like `REFRESH_TOKEN_STORAGE_KEY`, so a second preference cannot collide. */
const THEME_PREFERENCE_STORAGE_KEY = 'theme.preference';

const isThemePreference = (value: string): value is ThemePreference =>
  (Object.values(THEME_PREFERENCES) as string[]).includes(value);

/** `null` covers both "nothing stored" and a value this app version no longer recognises. */
export const readThemePreference = async (): Promise<ThemePreference | null> => {
  const stored = await AsyncStorage.getItem(THEME_PREFERENCE_STORAGE_KEY);

  return stored !== null && isThemePreference(stored) ? stored : null;
};

export const writeThemePreference = async (preference: ThemePreference): Promise<void> => {
  await AsyncStorage.setItem(THEME_PREFERENCE_STORAGE_KEY, preference);
};
```

```ts
// src/theme/useThemePreference.ts
import { colorScheme } from 'nativewind';
import { useCallback, useEffect, useState } from 'react';

import {
  readThemePreference,
  THEME_PREFERENCES,
  type ThemePreference,
  writeThemePreference,
} from './themePreferenceStorage';

export interface ThemePreferenceValue {
  preference: ThemePreference;
  setPreference: (next: ThemePreference) => void;
}

/**
 * The one thing NativeWind's own `colorScheme` does not expose (D2/D3 in
 * docs/superpowers/specs/2026-09-22-dark-mode-design.md): which of
 * 'system' | 'light' | 'dark' the user actually chose, as opposed to what it
 * resolves to. Every caller hydrates independently from storage and applies
 * what it reads — safe because storage is the one source every mount
 * converges on, and only a user action (never two mounts at once) writes to it.
 */
export const useThemePreference = (): ThemePreferenceValue => {
  const [preference, setPreferenceState] = useState<ThemePreference>(THEME_PREFERENCES.SYSTEM);

  useEffect(() => {
    let isMounted = true;

    const hydrate = async () => {
      const stored = await readThemePreference();

      if (!isMounted || stored === null) {
        return;
      }

      setPreferenceState(stored);
      colorScheme.set(stored);
    };

    hydrate();

    return () => {
      isMounted = false;
    };
  }, []);

  const setPreference = useCallback((next: ThemePreference) => {
    setPreferenceState(next);
    colorScheme.set(next);
    writeThemePreference(next);
  }, []);

  return { preference, setPreference };
};
```

```tsx
// src/theme/ThemeProvider.tsx
import type { PropsWithChildren } from 'react';
import { vars } from 'nativewind';
import { View } from 'react-native';

import { useThemeColors } from './useThemeColors';
import { useThemePreference } from './useThemePreference';

const CSS_VARIABLE_PREFIX = '--color-';

/**
 * Applies the active theme to the whole app via NativeWind's `vars()` (D1 in
 * docs/superpowers/specs/2026-09-22-dark-mode-design.md), and triggers
 * `useThemePreference`'s boot-time hydrate-and-apply effect (D3) — this
 * component itself never reads that hook's return value.
 */
export const ThemeProvider = ({ children }: PropsWithChildren) => {
  useThemePreference();
  const activeColors = useThemeColors();
  const cssVariables = vars(
    Object.fromEntries(
      Object.entries(activeColors).map(([key, value]) => [`${CSS_VARIABLE_PREFIX}${key}`, value]),
    ),
  );

  return (
    <View className="flex-1" style={cssVariables}>
      {children}
    </View>
  );
};
```

```md
# Theme

Design tokens para o app inteiro, mais o mecanismo de dark mode. `tokens.js`
é a fonte única da verdade e é propositalmente CommonJS: o mesmo arquivo
alimenta o `tailwind.config.js` (Node) e o código TypeScript, então um token
nunca diverge entre os dois.

Não há `.d.ts` escrito à mão: o TypeScript infere os tipos do próprio
`tokens.js` (`allowJs`), então um degrau de escala que não existe —
`colors.brand[5000]`, `colors.success[100]` — é erro de compilação, e um
tipo escrito à mão não tem como ficar defasado em relação ao arquivo.
`index.ts` reexporta para o código do app.

## Components

| Name | Description |
| ---- | ------------- |
| `ThemeProvider` | Aplica o tema ativo no app inteiro via `vars()` do NativeWind numa `View` raiz, e dispara o efeito de boot do `useThemePreference`. Montado em `App.tsx`, dentro do `GestureHandlerRootView`. |

## Hooks

| Name | Description |
| ---- | ------------- |
| `useThemeColors()` | O mapa semântico ativo (`semanticColors` ou `semanticColorsDark`), para o raro caso que precisa de um valor literal fora do NativeWind — uma cor de `ActivityIndicator`, por exemplo. |
| `useThemePreference()` | `{ preference, setPreference }`. `preference` é `'system' \| 'light' \| 'dark'` — a escolha do usuário, não o valor resolvido (o `colorScheme` do NativeWind só devolve o resolvido). Hidrata do `AsyncStorage` no mount e aplica via `colorScheme.set()`; `setPreference` grava e aplica na mesma chamada. |

## Constants

| Name             | Description                                                          |
| ---------------- | ---------------------------------------------------------------------- |
| `colors`         | Escalas brutas: `brand` e `neutral` (50→950), mais `success`, `warning`, `danger`, `info`. |
| `semanticColors` | Aliases por papel no tema claro: `background`, `surface`, `content`, `primary`, `border`, `danger`, … |
| `THEME_PREFERENCES` | `system` \| `light` \| `dark` — os três valores de `useThemePreference().preference`. |
| `spacing`        | Grid de 4pt, como strings CSS.                                        |
| `typography`     | `fontFamily`, `fontSize` (com line heights), `fontWeight`.            |
| `radius`         | Escala de border radius.                                              |

## Functions

| Name              | Description                                                        |
| ----------------- | ------------------------------------------------------------------ |
| `parsePixels(value)` | Converte um token CSS (`'16px'`) para o número que as APIs nativas esperam (`16`). |

## Types

| Name     | Description                        |
| -------- | ------------------------------------ |
| `Tokens` | Formato do objeto de tokens inteiro, inferido de `tokens.js`. |
| `ThemePreference` | União derivada de `THEME_PREFERENCES`. |

## Conventions

- Os valores são strings CSS (`'16px'`), não números: o NativeWind compila
  Tailwind para CSS antes de converter para estilos nativos, e números soltos
  não são CSS válido.
- As telas usam classes Tailwind, não estes exports. Importe daqui só quando
  uma API não passa pelo NativeWind — uma cor de `ActivityIndicator`, uma lib
  de gráficos.
- **Dark mode funciona através de variáveis CSS aplicadas em runtime**, não de
  um arquivo `.css` estático nem de classes `dark:` espalhadas pelas telas —
  ver decisão D1 em
  [`docs/superpowers/specs/2026-09-22-dark-mode-design.md`](../../docs/superpowers/specs/2026-09-22-dark-mode-design.md).
  `tailwind.config.js` mapeia cada alias semântico para `var(--color-<alias>)`;
  o `ThemeProvider` é quem decide o valor de cada variável, lendo
  `semanticColors` ou `semanticColorsDark` conforme o tema ativo. Uma tela que
  já usa `bg-background`/`text-content`/`bg-primary` não precisa de nenhuma
  mudança para funcionar nos dois temas.
- Um alias com o mesmo nome de uma escala sombreia a escala inteira no Tailwind,
  porque o `tailwind.config.js` espalha `semanticColors` depois de `colors`. É o
  caso de `danger`: `bg-danger` e `bg-danger-surface` existem, `bg-danger-500`
  não. Escolha o nome do alias com isso em mente.

## Adapting to a new app

1. Substitua a escala `colors.brand`.
2. Revise `semanticColors` e `semanticColorsDark` se a marca precisar de
   superfícies ou contraste diferentes nos dois temas.
3. Para uma fonte customizada: carregue com `expo-font`, depois defina `typography.fontFamily.sans`.

Nenhuma tela precisa ser tocada.
```
